# PR #36 — vector `simd_sum` in the fused decode attention: full refutation

**Verdict: dead hypothesis. Nothing here ships.** The vector reduction is
bit-exact, as nezuko showed, and it is worth **nothing** — alone or stacked on
the merged padding. A reduction that genuinely issues 25% fewer shuffles is
*slower*. The scored surface on this branch is byte-identical to `BASE_SHA`.

## Correction to the assignment's premise

The arm was built on a row from my #30 non-wins table:

```
float2 simd_sum    29.98 us/layer   vs control 32.03   =  -6.4%
your merged pad    30.01 us/layer   vs control 32.03   =  -6.3%
```

read as "vector reduction alone is worth −6.4%, the same size as the padding".
It is not. That row was `probe_padvec`, generated by
`diag_epilogue.py:vector_reduce(pad(src))` — **padding plus** float2. It never
contained a padding-free vector arm, so the two rows were the same mechanism
measured twice, differing by nothing. My label was ambiguous and I should have
written `pad+float2`; the docstring in that file already said "measured: no
gain", meaning no gain *over the padding it contained*.

Part 0 was the right instrument anyway, because it produced the arm that was
actually missing (C: vector, no padding) and a noise floor.

## Method

`senpai/tools/sliding-attn-probe`, the isolated harness calibrated in #30 to
0.77% against an end-to-end pair. Every arm is generated by
`diag_stack.py` from **one** rendered kernel text, so the control differs from
each candidate only by the mechanism under test:

| arm | exchange stride | QK cross-lane reduction |
| --- | --- | --- |
| `a_control` | `BDP = BD` (32) | 4 x scalar `simd_sum` |
| `b_pad` | `BDP = BD+1` (33) — **shipped** | 4 x scalar `simd_sum` |
| `c_vec2` | 32 | 2 x `simd_sum(float2)` (head pair) |
| `d_padvec2` | 33 | 2 x `simd_sum(float2)` |
| `e_vec4` | 32 | 1 x `simd_sum(float4)`, `pipe_kb` madds hoisted |
| `f_padvec4` | 33 | 1 x `simd_sum(float4)`, madds hoisted |
| `g_padvec4ep` | 33 | `f` + float2/float4 packing of the **epilogue** reductions |
| `h_padtree4` | 33 | hand-written 15-shuffle tree (see below) |

Control is `BDP = BD`: a one-token revert of the shipped padding that leaves
every other character identical, so `a` is the true pre-#30 addressing.

Noise floor is measured, not assumed: the same `.metal` file is loaded twice
under two labels (`a1`/`a2`, `b1`/`b2`) inside the same round-robin, so the
spread between them is pure measurement noise at identical code.

## What the numbers say

1. **The vector reduction alone (C) is worth −0.27% ± 0.3%,** i.e. a mean of
   one noise floor, and one twenty-fifth of the padding. The −6.4% attributed
   to it was the padding it was carrying.
2. **It does not stack (D, F, G).** Against the shipped `b_pad`, the float2,
   float4-with-hoisted-madds, and float4-plus-packed-epilogue arms land at
   −0.85%, +0.23%, −0.47%, +0.12%, −0.46%, −0.19%. Mean −0.27%, sign not
   stable, magnitude at the noise floor. There is no second win here.
3. **The advisor's outcome 2 is what happened**, but for a simpler reason than
   "the same stall measured two ways": arm C isolates the vector reduction with
   the padding removed and it does nothing *there* either. The mechanisms are
   not redundant — one of them is empty.

## The arm that should have worked, and why its failure is the real result

`simd_sum` on a vector is packing, not a cheaper reduction: four values still
walk four 5-level butterflies, 20 shuffles. So I built the arm that actually
removes shuffles.

Butterfly levels `xor 1` and `xor 2` leave every lane of a 4-lane group holding
the *identical* partial (fp add is bitwise commutative, which is exactly why
`simd_sum` can return one value to every lane). So after two levels each lane
can select the single value it is responsible for, `slot = lane & 3`, finish
that one alone with `xor 4, 8, 16`, and broadcast:

```text
4 values x 2 levels   =  8 shuffles
1 value  x 3 levels   =  3 shuffles
4 broadcasts          =  4 shuffles
                        ---
                        15   vs 20 for four independent butterflies
```

The xor sequence, and therefore each value's addition tree, is bit-for-bit the
one `simd_sum` walks — confirmed empirically: `h_padtree4` reports 0 mismatches
on all 8192 outputs, which is also an independent local confirmation that Metal's
`simd_sum` is the ascending xor butterfly.

**It is 1.79% slower.** A 25% cut in cross-lane shuffle count made the kernel
worse. That kills the family properly, not just the packing form of it:

- the QK reduction's cost is **not** proportional to shuffle issue count, so no
  bit-exact reduction restructure recovers the 3.58 us;
- what `h` traded away is instruction-level parallelism — four independent
  5-deep chains that interleave, replaced by a 2-deep phase, then a **single**
  3-deep chain with ILP 1, then four broadcasts dependent on it, plus the
  `lane & 3` select chain;
- and `e`/`f`, which hoist the second half's madds specifically to overlap the
  chains, gained nothing, so the existing 32 simdgroups per threadgroup already
  hide this latency.

The honest summary is that this loop tolerates the reduction's instruction cost
and punishes its dependency shape, and both the packing arms and the
shuffle-count arm leave one of those two untouched while damaging the other.

## AIR evidence (`xcrun metal -S -fno-fast-math -O2`)

The packing survives to AIR — it is not being discarded at the front end —
which makes the null a backend/hardware fact, not a source-level no-op:

| arm | `air.simd_sum` call sites |
| --- | --- |
| `a_control` | 11 x `f32` |
| `c_vec2` | 7 x `f32` + 2 x `v2f32` |
| `e_vec4` | 7 x `f32` + 1 x `v4f32` |
| `h_padtree4` | 7 x `f32`, plus 5 `simd_shuffle_xor` sites (11 dynamic after unroll) and 4 broadcast `simd_shuffle` sites |

## Geometry — this is not a re-tiling arm, so the M4 null transfers

| | control | every candidate |
| --- | ---: | ---: |
| threadgroups | 32 | 32 |
| threads/threadgroup | 1024 | 1024 |
| `maxTotalThreadsPerThreadgroup` | 1024 | 1024 |
| threadgroup memory | 17920 B | 18432 B (padded arms only) |
| waves, 20 cores (M4) | 2 | 2 |
| waves, 40 cores (M5) | 1 | 1 |

Under the programme's post-#7 doctrine these are instruction-mix changes at
**fixed** dispatch geometry, not thread re-tiling across cores. The wave count
is unchanged in every arm, so the M4 refutation is meaningful evidence for M5
rather than an M4 artefact. The residual M5 risk is only that a different
shader compiler could lower `simd_sum(float4)` better than the M4 one — but
that would have to conjure a win out of an arm whose upper bound here is
0.28% of a kernel that is 6.16% of decode, i.e. **0.017% of decode, 0.013% of
score**. Not worth an official receipt slot.

## Side result: a tighter number for the shipped padding

Three more within-process estimates of the merged #30 padding, on top of the
6.3% in that PR: **−7.8%, −6.8%, −6.8%** (medians). Mean of all four: **−6.9%**
of the sliding layer, tighter than the single sample the receipt was argued
from. At 31.5 us/layer and 30 sliding layers that is 65 us/step of a 14.6 ms M4
decode token = **0.44% of M4 decode**.

M5 projection, with the wave correction the advisor asked me to show in my own
table:

```text
saving is per threadgroup-wave:   65 us/step on M4 at waves = ceil(32/20) = 2
per-wave                          32.5 us
M5 waves                          ceil(32/40) = 1
M5 saving                         32.5 us/step
M5 decode token (receipt 0c21dc18) 4318.1 us
decode fraction                   32.5 / 4318.1 = 0.75%
score fraction                    0.75% x 0.75   = 0.56%
```

which lands on the advisor's ~0.6% correction rather than my original #30
0.9–1.2%. Recorded here so the next receipt narrative uses the right number.
