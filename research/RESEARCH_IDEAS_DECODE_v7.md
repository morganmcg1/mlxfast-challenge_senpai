## Idea 1: SYSTEMATIC GRID OVER-DISPATCH ELIMINATION ★★★★★

**Priority**: 1 (HIGHEST — systematic bug affecting every GEMV/QMV/norm/attention kernel)
**Component**: Decode (75% of score) — all kernels
**Status**: NOT tried, NOT in any exhausted list, NOT in any prior research file

### The Discovery

Every custom Metal kernel in the decode path uses the grid formula:

```
grid: (logical_tiles * threadGroupSize, 1, 1)
threadGroup: (threadGroupSize, 1, 1)
```

In Metal, `grid` is the **threadgroup count**, not total thread count (unlike CUDA
where `gridDim * blockDim = total threads`). Writing `logical_tiles *
threadGroupSize` for the grid dispatches `threadGroupSize`× more threadgroups
than needed. Each redundant TG computes identical results and writes to
out-of-bounds memory (harmless only because MLX's allocator pads output buffers).

**Kernels WITHOUT the bug** (correctly use `grid = logical_tiles`):
- Gate product softplus: `grid: (inVec)` with `threadGroup: (inVec)` — 1 TG ✓ (L3761)
- Router top-8: `grid: (256)` with `threadGroup: (256)` — 1 TG ✓ (L8970)
- Embedding+RoPE atlas: `grid: (512)` with `threadGroup: (512)` — 1 TG ✓ (L10721)
- Argmax stage 1: `grid: (224, 128)` with `threadGroup: (224)` — 2D grid ✓
- Threshold: `grid: (32)` with `threadGroup: (32)` — 1 TG ✓

The correct kernels confirm the pattern: grid = logical threadgroup count,
NOT total threads. The buggy kernels multiply by threadGroupSize.

### Root Cause

This is a **CUDA-to-Metal porting bug**. In CUDA, `<<<gridDim, blockDim>>>`
means `gridDim` blocks. To launch N blocks of T threads, you write `<<<N, T>>>`.
In Metal, `grid: (N, 1, 1), threadGroup: (T, 1, 1)` means N threadgroups.
Writing `grid: (N * T, 1, 1)` launches N*T threadgroups — T× too many.

Someone consistently wrote `logical_tiles * threadGroupSize` for the grid,
perhaps confusing Metal's grid (threadgroup count) with CUDA's grid (block count)
or thinking the grid needed to express total thread count.

### Why It Works Today

The redundant TGs all compute identical results (same inputs, same weights,
same arithmetic). They write to the same output locations as the valid TGs
(race-write-same-value) or to out-of-bounds locations (UB, harmless due to
MLX allocator padding). The correctness gates pass because the valid TGs
produce the correct output, and the redundant TGs' writes are either identical
or out-of-bounds-and-ignored.

### Bit-Exactness: YES (Class A — trivial)

Each kernel maps `tile = threadgroup_position_in_grid.x` to `out_row =
tile * rows_per_tile + simd_offset`. Tiles 0 to `logical_tiles-1` produce
valid output rows. Tiles >= `logical_tiles` produce out-of-bounds rows.
Reducing the grid to `logical_tiles` keeps ONLY tiles 0 to `logical_tiles-1`,
which are the exact TGs that produce the valid output. No arithmetic changes,
no reduction order changes, no precision changes. The output is bit-identical.

The redundant TGs' race-write-same-value pattern is actually UB in Metal
(concurrent writes to the same address are undefined even with same values).
Removing them makes the code MORE correct, not less.

### M5 Safety: YES

No `simd_sum(vec)`, no `dot(float4)`, no `*(thread float4*)` casts. Pure grid
geometry change — no kernel source modifications at all.

### Expected Savings

On a bandwidth-bound M5 (~89% GPU util), the redundant TGs consume:
1. **L2/SLC bandwidth**: Each redundant TG re-reads weights/KV-cache from L2
   (weights fit in L2 per-kernel: 2-8 MB, L2 is ~32-64 MB). The redundant reads
   compete for L2 bandwidth with useful work.
2. **GPU compute cycles**: Redundant FMAs and reductions waste ALU cycles.
3. **Threadgroup scheduling**: 64×-1024× more TGs to schedule across 40 cores.

Per-kernel estimates (redundant TGs eliminated, L2 bandwidth at ~4 TB/s):

| Kernel | Redundant L2 reads/layer | Layers | Total L2/step | Time at 4TB/s |
|---|---|---|---|---|
| Attention (1024×) | 1023 × 2 MB KV | 40 | 80 GB | ~20 µs |
| O-proj NVFP4 (64×) | 63 × 2.1 MB wgt | 40 | 5.3 GB | ~1.3 ms |
| QKV R1 (64×) | 63 × 1.5 MB wgt | 40 | 3.8 GB | ~0.9 ms |
| Norm+QKV (64×) | 63 × 1.5 MB wgt | 40 | 3.8 GB | ~0.9 ms |
| Gate/up QMV R1 (64×) | 63 × 9.4 MB wgt | 39 | 23 GB | ~5.8 ms |
| Down+residual (288×) | 287 × 5 MB wgt | 39 | 56 GB | ~14 ms |
| Res+RMSNorm+Router (512×) | 511 × 8 KB | 39 | 0.16 GB | ~40 µs |
| LM head coarse (512×) | 511 × 134 MB codes | 1 | 68 GB | ~17 ms |

Note: LM head coarse reads 134 MB of int5 codes (vocab × 1344 B/row). With
512× over-dispatch, the first read per row goes to DRAM and subsequent reads
hit L2/SLC (134 MB may partially fit in 48-64 MB SLC). Effective redundant
traffic is ~67 GB of SLC reads.

**Conservative total estimate**: ~8-15 ms of redundant L2/SLC bandwidth per
decode step. At a ~10 ms decode step, this is **80-150% of decode time** —
meaning the GPU is spending most of its time on redundant work!

Even if asyncEval overlap hides 50% of this, the net savings are still
~4-7 ms = **40-70% decode speedup**.

**Score impact**: 40-70% decode × 0.75 = **30-52% total score**.

This is conservative — the actual savings depend on L2 hit rates, GPU
scheduling, and asyncEval overlap. Even a 10% decode speedup (the pessimistic
case if most redundant reads hit SLC) gives 7.5% total score.

### Budget: ~0 bytes

Each change is removing `* threadGroupSize` from the grid expression. For
example: `(heads / 2) * 1024` → `heads / 2`. The `* 1024` token is replaced
by nothing. Net byte change is NEGATIVE (fewer characters in grid expressions).

### M4 Testability: YES

Pure grid geometry change. No kernel source modifications. Verify via:
1. `swift test --force-resolved-versions` (correctness gates)
2. `./benchmark.sh --local-iterate` (timing: compare s/token before/after)
3. `research/run_upstream_equivalence.sh` (upstream equivalence)

### Risk Assessment

**LOW risk for correctness**: The valid TGs (tiles 0 to logical_tiles-1) are
unaffected. The redundant TGs are removed. Output is bit-identical.

**MEDIUM risk for timing**: The grid reduction may not produce the expected
speedup if:
1. Metal's GPU scheduler is smart about skipping redundant TGs (unlikely)
2. The redundant reads all hit SLC (large cache), making the L2 savings small
3. asyncEval overlap already hides the redundant work

**The pessimistic case**: If Metal's scheduler is smart and skips redundant TGs,
the change is a no-op (0% speedup, 0% regression). The optimistic case is a
massive speedup. Either way, it's worth testing.

### Why This Wasn't Found Before

1. The pattern is systematic (every kernel has it), making it invisible to
   per-kernel analysis — it looks like "the way Metal grids work"
2. The redundant TGs don't cause crashes (UB writes to padded memory)
3. Timing analysis focused on dispatch count and DRAM bandwidth, not L2 bandwidth
4. The multiplier equals threadGroupSize, making it look intentional
5. Prior research notes (DEEP_CODE_ANALYSIS_V2) flagged the attention 1024×
   factor but were uncertain and didn't generalize to ALL kernels

### Recommended Testing Order

1. **O-proj NVFP4 first** (64×, 40 layers, largest weight reads): change
   `grid: ((outVec / 16) * 64, 1, 1)` to `grid: (outVec / 16, 1, 1)`. If this
   shows any speedup, the pattern is confirmed.
2. **Attention kernel** (1024×, 40 layers): change `grid: ((heads / 2) * 1024, 1, 1)`
   to `grid: (heads / 2, 1, 1)`. Highest multiplier, most redundant TGs.
3. **Down+residual** (288×, 39 layers): change the grid multiplier.
4. **All remaining kernels** if the first three show gains.

## Idea 2: ASYNC EVAL RE-OPTIMIZATION AFTER GRID FIX ★★★

**Priority**: 2 (follow-up to Idea 1)
**Component**: Decode (75% of score) — all layers
**Status**: NOT tried (depends on Idea 1)

### Mechanism

The current asyncEval schedule (`at:0,1,7,15,23,31,39`) was tuned with the
over-dispatched kernels. After grid reduction (Idea 1), each kernel runs
N×-faster (where N is the threadGroupSize multiplier). The optimal asyncEval
schedule depends on relative kernel durations:

- If attention drops from ~300µs to ~1µs (1024× reduction), the GPU idle gap
  between layers shrinks, and fewer asyncEval rungs are needed
- If O-proj drops from ~1.3ms to ~20µs (64× reduction), the critical path
  shortens dramatically
- The optimal schedule may shift from 7 rungs to 2-3 rungs, or the stride
  may need to be shorter (every 4 layers instead of every 8)

### Expected Signal

After grid fix, sweep `DARKBLOOM_DECODE_ASYNC_STAGE` values:
- `at:0,1` (minimal — just front-edge)
- `at:0,1,3,5,7` (frequent early rungs)
- `at:0,1,7,15,23,31,39` (current default — may still be optimal)
- `ladder(4)`, `ladder(8)`, `ladder(10)`, `ladder(20)`

### Bit-Exactness: YES

asyncEval changes only timing, not arithmetic.

### M5 Safety: YES — env var knob, no kernel changes.

## Idea 3: LM HEAD COARSE KERNEL THREADGROUP REDUCTION ★★☆

**Priority**: 3 (1 dispatch per step, 512× over-dispatch)
**Component**: Decode (75% of score) — LM head
**Status**: NOT tried (covered by Idea 1 for grid, but this adds a further optimization)

### Mechanism

The LM head coarse kernel (LagunaLmHeadPrune.swift L935) uses:
```
grid: (vocab / 16 * 512, 1, 1)    // 6272 * 512 = 3,211,264 TGs
threadGroup: (512, 1, 1)
```

After Idea 1's grid fix: `grid: (vocab / 16, 1, 1)` = 6272 TGs of 512 threads.

Further optimization: the coarse kernel computes one 16-row tile per TG
(via `simdgroup_index_in_threadgroup` = 0..15). With 512 threads = 16
simdgroups, only 16 simdgroups are used, but the threadgroup has 16. This
is already optimal after the grid fix.

However, the int5 code read is 1344 B/row × 100352 rows = 134 MB. After the
grid fix, this is read once (6272 TGs × 16 rows × 1344 B = 134 MB). The kernel
is still bandwidth-bound by the int5 code read.

### Expected Signal (after grid fix)

The grid fix alone should save ~17ms of redundant L2/SLC reads (512×
over-dispatch of 134 MB int5 codes). The further optimization is:
- Could the threadgroup be reduced from 512 to 256 (8 simdgroups, still
  16 rows but 2 rows per simdgroup)? This would halve the threadgroup size
  and improve occupancy.

### Bit-Exactness: YES (grid fix) / MEDIUM (threadgroup change)

The grid fix is bit-exact (Idea 1 argument). The threadgroup reduction
changes the per-row computation: with 512 threads, each simdgroup handles
1 row; with 256 threads, each simdgroup handles 2 rows. The K-loop
accumulation order changes, which could change FP rounding.

### Budget: 0 bytes (grid fix), ~200 bytes (threadgroup variant)

### M4 Testability: YES

## Idea 4: ROUTED DOWN WEIGHT PACKED SCALES BANK ★★☆

**Priority**: 4 (bandwidth reduction for down kernel, 39 layers)
**Component**: Decode (75% of score) — MoE down projection
**Status**: NOT tried (mentioned in DEEP_CODE_ANALYSIS_V2 Area D1 but never assigned)

### Mechanism

The routed gate/up QMV kernel uses a packed (walk-order interleaved) scales
bank (`DARKBLOOM_PACKED_SCALES`, L10005). This reorders scale bytes to match
the kernel's code access pattern, improving memory transaction coalescing.

The routed DOWN kernel (`lagunaRoutedSharedDownResidual`, L7826) does NOT use
packed scales. It reads weight codes and scales from two separate tensors:
```
const device uint8_t* scale = expert_scales + output_row * scale_row_bytes + lane / 2;
```

The scale access pattern is: 16 bytes per row (halved), 2 threads per byte.
This is contiguous within a row but strided across rows (16-byte stride).
With 8 output rows per TG, the scale reads span 8 × 16 = 128 bytes — one cache
line. This is already fairly efficient.

However, the down weight codes are read as `expert_weight + output_row *
packed_row_bytes + lane * 8` (256 bytes per row, 32 threads × 8 bytes each).
The codes and scales are in separate tensors, requiring two device streams.
Packing scales inline with codes (or in a walk-order bank) would reduce
to one stream.

### Expected Signal

The down kernel reads per layer:
- 9 experts × 2048 rows × 256 bytes (codes) = 4.7 MB
- 9 experts × 2048 rows × 16 bytes (scales) = 295 KB
- Total: ~5 MB per layer, 39 layers = 195 MB/step

Packed scales would save ~295 KB/layer = 11.5 MB/step of separate scale
stream overhead. At 614 GB/s: ~19 µs. Small but nonzero.

### Bit-Exactness: YES

Scale reordering is a permutation — same bytes, different order. The kernel
reads the same scale values, just from a different address pattern.

### M5 Safety: YES — no forbidden constructs.

### Budget: ~2-4 KB in LRM (new bank preparation function + kernel input changes)

### M4 Testability: YES

### Risk: MEDIUM — the down kernel's scale access is already contiguous.
The gain may be negligible. Test only if grid fix (Idea 1) doesn't fully
close the bandwidth gap.

## Idea 5: GATE SOFTPLUS 4× SCALE/BIAS DEDUP VIA simd_shuffle ★☆☆

**Priority**: 5 (small bandwidth, only on non-default path)
**Component**: Decode — gate softplus kernel (fallback path)
**Status**: NOT tried (mentioned in BANDWIDTH_AUDIT but never assigned)

### Mechanism

The `lagunaGateSoftplusSource` kernel (L4307) reads INT8 affine scales/biases
with `lane/SS` where `SS = GS/V = 32/8 = 4`. This means 4 consecutive lanes
(0-3, 4-7, ...) read the SAME scale and bias value — a 4× redundant device load.

The existing code already uses `simd_shuffle` for the scale/bias broadcast:
```metal
if(lane==gl){ s=float(pm[row*KG*2]); b=float(pm[row*KG*2+1]); }
s=simd_shuffle(s,gl); b=simd_shuffle(b,gl);
```

Wait — the code ALREADY does the dedup! `lane==gl` (where `gl = (lane/SS)*SS`)
loads the scale/bias once per 4-lane group, then `simd_shuffle` broadcasts.
The BANDWIDTH_AUDIT noted this but may not have realized the code already
handles it.

### Status: ALREADY IMPLEMENTED

The `simd_shuffle` broadcast at L4333-4334 already eliminates the 4× redundant
device load. No further optimization needed.

### Priority: NONE (dead end — already done)

## Idea 6: KV CACHE L2 LOCALITY OPTIMIZATION FOR SLIDING ATTENTION ★☆☆

**Priority**: 6 (after grid fix, attention becomes compute-bound)
**Component**: Decode (75% of score) — 30 sliding layers
**Status**: NOT tried

### Mechanism

After the grid fix (Idea 1), the attention kernel runs with only `heads/2`
threadgroups (32 for sliding, 24 for full). Each TG reads the full 512-position
KV cache for its head-pair.

For sliding layers (30 of 40), the KV cache is a ring buffer of 512 positions
× 8 KV heads × 128 BF16 × 2 (K+V) = 2 MB per layer. With 30 layers, the total
KV cache is 60 MB — larger than L2 (~32-64 MB).

After grid fix, the attention kernel reads 2 MB per layer from DRAM (since
60 MB > L2). With the current 1024× over-dispatch, the first TG brings the
KV cache to L2 and the 1023 redundant TGs hit L2. After the grid fix, every
TG goes to DRAM (no L2 warming from redundant TGs).

This could make the grid fix SLOWER for attention if the KV cache doesn't fit
in L2! The redundant TGs were inadvertently warming the L2 cache.

### Mitigation

If the grid fix regresses attention, consider:
1. **Keep a small grid multiplier for attention only** (e.g., 2× instead of
   1024×) to provide some L2 warming
2. **Or reorder layer processing** so adjacent layers' attention kernels
   share L2 cache (currently layers are processed sequentially, and each
   layer's KV cache is at a different address)

### Expected Signal

If attention regresses after grid fix: try `grid: (heads/2 * 2, 1, 1)` (2×
multiplier instead of 1024×). This provides 1 redundant TG for L2 warming
while still eliminating 1022/1024 of the redundant work.

### Bit-Exactness: YES (same argument as Idea 1 — 2× is still redundant with
race-write-same-value, just less so)

### Budget: 0 bytes

### M4 Testability: YES

### Risk: MEDIUM — this is a fallback if Idea 1 regresses attention.

## Idea 7: EMBEDDING + FIRST LAYER NORM FUSION ★☆☆

**Priority**: 7 (1 dispatch saved, very small gain)
**Component**: Decode — 1 dispatch per step
**Status**: NOT tried (DEEP_CODE_ANALYSIS_V2 OPP-7c considered but rejected)

### Mechanism

The embedding+RoPE atlas kernel (L10444) produces the hidden vector (2048 BF16).
Layer 0's attention then does norm+QKV (1 dispatch). The hidden vector is
written to memory by the embedding kernel and re-read by the norm+QKV kernel.

Fusing the norm into the embedding kernel would eliminate the 2048 BF16
write+read = 8 KB. But the embedding kernel also produces RoPE angle rows
consumed by ALL layers, so the fusion is complex.

### Why Low Priority

- Only 1 dispatch saved per step (out of ~284)
- The hidden vector is only 4 KB — negligible bandwidth
- The embedding kernel produces 3 outputs (hidden, full angles, sliding angles)
- Adding norm computation would complicate the kernel and increase its
  threadgroup memory usage

### Budget: ~500 bytes in LRM (new kernel variant)

### Risk: LOW but gain is negligible

### Primary Recommendation

**Idea 1 is the single most impactful discovery in this analysis.** The
systematic grid over-dispatch (`grid = logical_tiles * threadGroupSize`
instead of `grid = logical_tiles`) affects every GEMV/QMV/norm/attention
kernel in the decode path. The fix is ~16 one-line changes (remove the
multiplier from each grid), costs zero bytes, is bit-exact, and could
save 10-50% of decode time.

**Test the O-proj kernel FIRST**: change `grid: ((outVec / 16) * 64, 1, 1)`
to `grid: (outVec / 16, 1, 1)` at L4493. This is the safest single-kernel
test (64× over-dispatch, 40 layers, no cross-TG dependency). If timing
improves, the pattern is confirmed and all other kernels can be fixed.

**CRITICAL CAVEAT**: After grid fix, attention kernels that previously had
their KV cache warmed by 1023 redundant TGs may regress (Idea 6). If attention
timing worsens, use a 2×-4× multiplier for attention only (still 256-512×
reduction from 1024×).

### What Was Verified and Ruled Out

- Gate softplus 4× scale dedup (Idea 5): ALREADY implemented via `simd_shuffle`
- Shared gate/up scale halving: ALREADY wired (PR #180 fix)
- Router top-8 + residual+RMSNorm fusion: DEAD (1-tile parallelism loss)
- Final RMSNorm → LM head fusion: DEAD (PR #276, 3 barriers >> 5.8µs saved)
- Input-vector staging: DEAD (barrier overhead > LSU relief)
- Attention epilogue 1-pass merge: DEAD
- RMSNorm fusion: DEAD (FP reduction order changes flip tokens)

### Key Architectural Insight

The decode path is NOT as well-optimized as prior research assumed. While
dispatch fusion is excellent (7 dispatches/layer), every kernel is launching
64×-1024× more threadgroups than needed. This wastes L2 bandwidth, GPU
compute, and threadgroup scheduling resources. The systematic nature of
the bug (multiplier = threadGroupSize in every kernel) suggests it was
introduced once and propagated through copy-paste.

The fact that prior timing analysis didn't catch this is because:
1. The redundant TGs' output writes are harmless (UB with padding)
2. L2 bandwidth isn't directly measured (only DRAM bandwidth and dispatch
   count are tracked)
3. asyncEval overlap masks some of the redundant work
4. The multiplier = threadGroupSize makes it look intentional
5. Per-kernel analysis sees the pattern as "the way Metal grids work" rather
   than a bug

This is the kind of systematic issue that a fresh pair of eyes (or a
systematic audit) catches that incremental optimization misses.
