## 1. Goal and the shape of the score

The scored window is one 512-token prefill forward plus a teacher-forced decode
pass (512-token seed + 128 one-token steps), and

```
score = decode_speedup^0.75 * prefill_speedup^0.25
```

Because the seed forward is charged into the decode metric as well, the true
elasticities at our operating point are **0.362 for the 512-token seed forward**
and **0.638 for the marginal steady decode step**, not 0.25/0.75. Writing `S` for
the seed forward in ms and `T` for the marginal steady step:

```
S = 512000 * prefill_seconds_per_token
T = 1000 * decode_seconds_per_token - S / 128
```

Everything below is a **prefill-axis** (i.e. `S`) arm. At the current operating
point one millisecond off `S` is worth **0.3781 % of score**.

## 2. Where the prefill milliseconds are, and why almost every idea is worth zero

The dominant single cost in the 512-token prefill forward is the routed MoE
gather-GEMM, dispatched as `fp_gather_qmm_rhs_expert_nax`
(`Vendor/mlx-swift/Source/Cmlx/mlx/mlx/backend/metal/kernels/fp_quantized_nax.h`,
selected in `.../metal/quantized.cpp`). Two independent derivations of its
weight traffic agree to the byte:

```
768 load_unsafe per chunk  x  2304 B  x  8379 chunks  =  14,826,405,888 B
```

From that, on the ranked host:

* issued arithmetic intensity **87.66 FLOP/byte** against a machine balance of
  **98.36 FLOP/byte** => the kernel is **memory-bound, not compute-bound**;
* cache-immune weight-byte floor **24.306 ms**; issued-MMA floor **23.757 ms**.

The MMA floor is *already below* the byte floor. That single inequality kills an
entire family of proposals — anything whose mechanism is "issue fewer MMA rows"
(sub-16 SM, tile-quantisation padding, routing-aware two-regime dispatch,
banding) is worth **approximately zero milliseconds**. Expert-traffic pruning is
also approximately zero: expert occupancy is 79.74 %, so the actual 14.826 GB is
already 86.1 % of the all-dense 17.213 GB.

We also have a long list of *measured* nulls on this kernel from earlier rounds:
in-kernel prefetch, depth-2 software pipelining, double-buffered weight staging,
alternative barrier placement, scale-load amortisation (nulled *even though the
issue count fell*), and threadgroup-memory swizzling (the existing `+8`-element
pad already puts the staging pitch at 36 words = 4 mod 32, i.e. at the 2-cycle
bank-conflict floor).

**What is left.** The weight stream is incompressible and the math is not the
binding constraint, so the only compressible stream in the kernel is the
**A operand (the sorted activation rows), which is re-read across `grid.x`.**

## 3. The lever

Dispatch geometry at the shipped default:

```
group_dims = (32, WN, WM) = (32, 1, 4) = 128 threads = 4 simdgroups
grid_dims  gate/up (N/BN, egroups, 1) = (16, 256, 1) = 4096 threadgroups
           down                        = (32, 256, 1) = 8192 threadgroups
```

The **weight** tile is staged in threadgroup memory (`Ws_storage[BN * (BK+8)]` =
64 x 72 x 2 B = 9,216 B, which is 99.91 % of the kernel's threadgroup
allocation). The **A operand is not staged** — each simdgroup pulls its sorted-x
fragments straight from device memory. Since `grid.x = N/BN`, the same x rows are
pulled by 16 threadgroups for gate/up and 32 for down.

Widening `BN` from 64 to 128 **halves `grid.x`**, and therefore halves the
inter-threadgroup A-operand device traffic, at constant MMA work and constant
weight traffic.

Sizing (38 layers, 4096 sorted rows):

* gate/up A operand 4096 x 2048 bf16 = 16.8 MB/layer, re-read 16x;
* down A operand 4096 x 512 bf16 = 4.19 MB/layer, re-read 32x;
* zero-reuse corner = 30.765 GB of A traffic across the forward.

## 4. Why the headline number is smaller than it looks (a self-refutation)

The obvious way to price this is "halve 30.765 GB, divide by DRAM peak". That is
**arithmetically impossible**, and we published the refutation before spending a
receipt:

```
30.765 GB / 43.262 ms = 711 GB/s   vs a 610 GB/s peak  ->  16.6 % over peak
```

So the A stream cannot all be coming from DRAM: some fraction `r` of it is
already absorbed by cache. The weight traffic alone forces **`r >= 0.302`**,
hence **`r <= 0.698`** and the **prize is bounded above by 8.76 ms**, not the
8.4 ms of *guaranteed* saving the first draft of this arm claimed. Conversely,
the 3-sigma detection bar of **1.35 ms** needs only **`r >= 0.303`**, so the
design gate is *not* closed either. Uncertainty on `r` is sigma_r = 0.033.

That is the honest prior for this experiment: **two-sided, roughly a coin flip.**
Either the re-reads are real DRAM traffic (up to ~8.8 ms on the table, a record
gain) or the system-level cache already absorbs them (approximately 0 ms, and the
routed gather-GEMM has *no remaining ranked lever at all*). Both answers are
worth publishing; the second one closes the largest open family in our research
programme.

## 5. Implementation, and the two bugs a naive `BN=128` edit walks into

The variant is selected host-side in
`Vendor/mlx-swift/Source/Cmlx/mlx/mlx/backend/metal/quantized.cpp`. The shipped
default is `bm=64, bn=64, bk=64, wm=4, wn=1`. We added three new variants —
`bn=128` for both routed shapes, for gate/up only, and for down only — guarded on
the two Laguna MoE shapes `(K=2048,N=1024)` and `(K=512,N=2048)`, because
widening an arbitrary shape would drop it out of the `expert_aligned` predicate
and into an untested generic instantiation with no fused SwiGLU.

`expert_aligned` requires
`align_N && align_K && bm == 64 && wm == 4 && (wn == 2 || wn == 1)`; `bn` enters
only through `align_N = (N % bn) == 0`, and `1024 % 128 == 0`, `2048 % 128 == 0`.
So the expert path survives. `WN` must stay 1: with `WN = 2`, two simdgroups in
the same threadgroup own the same rows and each loads the A fragments
separately, which *doubles* intra-threadgroup A traffic — the opposite of this
lever.

Two things then break, and both had to be repaired before the arm measures the
lever rather than a regression:

**(a) A silent wide-load regression, invisible to the obvious probe.** At
`bn = 128` the per-thread source stride doubles, `kSrcBytes` goes 16 -> 32, and
that makes the `kWideLoadShapeOk` / `kWideLoad8ShapeOk` predicates *statically
false* — the loader degrades to 32 scalar 1-byte loads per thread per
k-iteration. But the host-side `..._wide_load_ok()` helper still returns true, so
**the emitted kernel name still reads `_ws_1_wl_1`.** A name-string check — the
natural test, and the one our own design brief specified — would have **passed
while the loader was degraded.** This is the same failure mode as an earlier
finding on the K axis (widening `BK` silently disabling the widened device load),
now shown to recur on the N axis. Repair: a `WideSrc32` path that issues two
16-byte vector loads instead of one, bit-exact because the intra-tile offset is
zero.

**(b) A wrong SwiGLU pairing.** The register-local fused-SwiGLU epilogue is
gated on `(WN==1) && (BN==64) && ((BM/WM)==16)`, so at `BN = 128` it turns off
and control falls to the threadgroup-staged epilogue. That staged epilogue pairs
column `c` with column `c + BN/2`, i.e. `c + 64` at `BN = 128` — but the host
packs gate/up with `pairRows = 32` inside each 64-wide block. Repair: make both
epilogues 64-block aware so the pairing is `c <-> c + 32` within each 64-block
regardless of `BN`.

Both repairs are proved **inert at `BN = 64`** by byte-identical compiled AIR
(39,392 B before and after), which is what makes the control arm in this ladder a
legitimate control.

Resource cost of the wide tile, disclosed because it is the leading alternative
explanation if an arm loses: threadgroup memory goes 9,232 -> 18,448 B, and
per-thread accumulator floats go 32 -> 64 (`TN = SN/16` goes 4 -> 8), pushing the
register estimate from ~80 to ~144. On the ranked host this could reduce
occupancy enough to eat the saving. It cannot be settled off-M5.

## 6. Why every number in this arm comes from an official receipt

`metal::is_nax_available()` requires macOS >= 26.2 **and GPU architecture
generation >= 17**. Our M4 Pro development hosts report generation 16 and there
is no environment override, so `fp_gather_qmm_rhs_expert_nax` is **never entered
locally** — the gate falls back to a different kernel family. Measured
separately: **94.2 % of prefill GPU time on an M4 Pro runs Metal functions the
ranked M5 never executes.**

Consequences we accept explicitly:

* No local benchmark, no local timing, and no runtime kernel-name printf can
  exercise the lines this arm changes inside the `_nax` kernel. All local
  evidence is static: offline `metal` compiles, AIR diffs, issue counting from
  source, and a byte-exact reproduction of the host-side naming logic.
* The generated twin
  `Vendor/mlx-swift/Source/Cmlx/mlx-generated/fp_quantized_nax.cpp` is what the
  runtime actually JIT-compiles for this kernel (the package excludes the whole
  `backend/metal/kernels` directory from the build), so a header-only edit does
  nothing. The header and the twin are kept byte-consistent and checked
  mechanically before every submission.
* Therefore the ladder below is the *instrument*, and a rejected receipt is a
  perfectly good measurement: it still returns full `decode_seconds_per_token`
  and `prefill_seconds_per_token`.

## 7. Measurement discipline

Three rules, each learned from a specific past error in this programme:

1. **Price the arm against the candidate prefill wall plus a contemporaneous
   control set, never against the paired baseline.** Same-session *baseline*
   prefill wanders about 5 % between sessions (it is bimodal, with a 3.61 % gap
   between modes), while the *candidate* prefill wall has sd 0.14 %. Using the
   published ratio as the observable throws away an order of magnitude of
   precision.
2. **One receipt per commit, ever, and the distinguishing byte must live inside a
   submitted file** — the service dedupes byte-identical archives, and the
   archive contains only the editable paths, so a marker in a research file gets
   deduped away and you get the same archive back.
3. **An isolated-regime per-kernel measurement is an upper bound on the
   overlapped-regime saving, and its sign can even invert.** We have a measured
   counterexample in this campaign: one dial made its own kernel 6.4 us/step
   faster under a one-dispatch-per-command-buffer probe (12/12 sign) while making
   the whole decode step 34.6 us/step slower end-to-end (21/21 reps). The real
   stream overlaps 1222 dispatches per prefill, so per-kernel attribution is a
   map, not a price.

Channel precision, measured over 7 byte-identical receipt families: the 1-vs-1
receipt-difference sigma is **0.1588 % of score on the prefill channel** (versus
0.2601 % on decode). The 1.35 ms design bar is +0.51 % of score, i.e. **z ~ 3.2
from a single control/arm pair.**

## 8. The ladder, preregistered

```
A0  control: the same tree with the wide-tile variants present but the default
    unchanged (BN=64). Compiles to byte-identical AIR, so it is a true control.
A2  down projection only (K=512, N=2048) at BN=128.
A1  gate/up only (K=2048, N=1024) at BN=128.
A3  both, only if A1 or A2 is positive.

order: A0-1, A0-2, A2-1, A1-1, A0-3, A1-2, A2-2, spare
minimum 4 receipts, cap 8, >= 786 s inter-arrival.
```

**A2 (down) runs first, ahead of the bigger prize.** The fused-SwiGLU epilogue is
gated on the gate/up shape, so A2 exercises *only* the loader repair while A1
also carries the epilogue rewrite. A2 is the clean single-mechanism arm; A1 is a
compound. A2 also keeps 4096 threadgroups (down goes 8192 -> 4096), which is the
same threadgroup count gate/up already has at `BN = 64`, so A2's occupancy
perturbation is the smaller of the two.

Preregistered outcomes:

* **P (positive).** An arm buys >= 1.35 ms of prefill with the control set
  bracketing it => propose the composed arm.
* **N-1 (cache null).** Both arms inside +/- 1.35 ms => *the A-operand re-reads
  are already absorbed by cache, and the routed gather-GEMM has no remaining
  ranked lever.* This closes the family and is worth more than a marginal win.
* **N-2 (register-pressure null).** An arm is negative and the occupancy estimate
  predicted a spill => report the spill as the mechanism; do not retry with
  `BM = 32`, which leaves the expert-aligned envelope.

**Bit-exactness claim, stated as something that could be wrong.** `K` is never
split in this kernel family, so every output element accumulates over the
identical `K` order regardless of `BN`; only *which threadgroup owns a column*
changes. The register-local/staged epilogue choice is independently known to be a
bit-exact toggle, and the `WideSrc32` loader repair reads the same bytes in the
same order. So we expect `max_abs_diff = 0` and a prefill maximum absolute logit
error of 0. If a receipt comes back with anomalous metrics or a correctness
failure, the epilogue pairing is the first suspect, not the timing.

## 10. Caveats and what we would do next

* The occupancy confound (threadgroup memory 9,232 -> 18,448 B, registers
  ~80 -> ~144) is open and cannot be settled off the ranked host. If an arm
  loses, occupancy is the leading explanation and the lever is not thereby dead.
* The prize bound (`<= 8.76 ms`) rests on a published DRAM peak and one
  end-to-end marginal-rate estimate. If the true peak is higher, the bound moves.
* We do not claim any local timing evidence for this arm. There is none, by
  construction, on generation-16 hardware.
* Next step if a positive lands: compose the two shapes, then re-examine whether
  `BN = 256` is admissible for the down shape, where the accumulator cost is
  lower.
