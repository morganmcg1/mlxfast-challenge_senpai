## 0. How the JIT budget is actually spent (mechanism, verified)

The compile model is **lazy and name-keyed**, confirmed by reading the C++:

- `metal_kernel(...)` (common `metal_kernel.cpp:202-366`) returns a *closure*. It only
  builds the Swift wrapper at the `private let`; **no Metal compile happens at construction.**
- On first `kernel(...)`, the closure builds `kernel_name = "custom_kernel_" + name
  + template_hash + per-input-dtype + per-output-dtype` (`metal_kernel.cpp:289-316`).
- `CustomKernel::eval_gpu` (`custom_kernel.cpp:56-72`) calls
  `device.get_library(name_, source_)` — **first call with a new `name_` compiles the
  source into a Metal library; later calls reuse the cached PSO by `name_`.**

**Consequence:** a `private let` kernel that is never dispatched compiles **nothing**.
PR #359 confirmed all OFF-flagged kernels are properly lazy. So the M5 budget is driven
by **distinct `kernel_name` strings actually dispatched** in warmup + prefill + decode,
NOT by the 55 `metalKernel` declarations.

So the lever is: **reduce the number of distinct kernel_names dispatched in the scored
run + warmup**, and **delete eagerly-warmed kernels that are never scored-dispatched.**

## 2. Ranked consolidation / elimination opportunities

Each item lists the dispatch evidence, expected compile savings, and difficulty.
"Compile saved" = distinct `kernel_name` JIT compiles removed from the default run.

### ★★★ Opportunity 1 — Stop warming the never-scored full-attention kernel
**Target:** `lagunaFusedFullAttentionKernelWarmupEnabled` (L1777) and the warmup call
at `LagunaRuntimeWeights.swift:493-497` → `lagunaWarmFullFusedAttentionKernel()` (L2253).
**Evidence:** The warmup explicitly compiles `lagunaFullFusedAttentionKernel` (L1781)
with throwaway arrays. It is **never scored-dispatched**: the full-attention decode branch
(L5875) requires both `lagunaFusedFullAttentionEnabled` (ON) AND `useFusedFullQKNormYaRN`
(= `lagunaFusedFullQKNormYaRNEnabled` L523, **default OFF** `== "1"`). With YaRN OFF,
full-attention layers take the stock SDPA path (L5945-5980), so this kernel is pure warmup
waste — 1 full fused-attention compile (a large kernel: 1781-2250 ≈ 470 lines source).
**Savings:** **−1 JIT compile**, and a large/expensive one (big source → long compile).
**Fix:** default `DARKBLOOM_FUSED_FULL_ATTN_KERNEL_WARMUP=0` (change `!= "0"` → `== "1"`
at L1777-1779), or gate the warmup call on `lagunaFusedFullQKNormYaRNEnabled` too.
**Difficulty:** TRIVIAL (1-line flag flip). **Risk:** NONE for scoring (kernel unused);
only matters if a future experiment turns YaRN ON. Bit-exactness: untouched.
**Caveat:** confirm the full-attention kernel is genuinely never reached in any hidden
correctness gate (free-run/anchor) — if a hidden gate forces YaRN ON it would recompile
in-window. Verify with `lagunaTrace` on M5.

### ★★★ Opportunity 2 — Consolidate the 4 NVFP4 decode-QKV R1 kernels into 1 (function-constant)
**Target:** `lagunaDecodeNVFP4QKVR1Kernel` (4580), `lagunaDecodeNVFP4QKVR1HalvedKernel`
(4590), `lagunaFusedGProjQKVKernel` (4628), `lagunaFusedGProjQKVHalvedKernel` (4639).
**Evidence:** All four are generated by one function `lagunaDecodeNVFP4QKVR1Source(
halvedScales: Bool, withGProj: Bool)` (4446). They differ only by two booleans baked
into source: `halvedScales` changes a few address-arith lines (449-4471) and an extra
`qkv_escape` input; `withGProj` appends a gate-softplus branch (4472-4520) + outputs.
**Default dispatches only #1: `lagunaFusedGProjQKVHalvedKernel` (4639)** (halved ON,
withGProj ON). The other 3 are dead-by-default but still declared.
**Savings:** consolidation does not reduce the *default* compile count (only 1 of 4
compiles today), BUT it (a) removes 3 dead `metalKernel` declarations (~code budget,
safer), and (b) if the official harness ever toggles halving/g_proj it would collapse
4→1. More importantly, the **same pattern's `lagunaGatedAffineOProjNVFP4` family (Op. 4)
IS default-multi-compile** and benefits more.
**Fix:** drive `halvedScales`/`withGProj` via Metal `function_constant` (set at dispatch)
or a `template:` Int/Bool arg instead of source string interpolation; keep ONE kernel.
**Difficulty:** MEDIUM (function constants in MLX custom kernels require a
template-arg route; MLX's `template:` param already specializes by name, so a template
arg still produces N compiles — true savings needs a runtime branch + `[[function_constant]]`,
which MLX `metalKernel` does not expose directly). A simpler win: **delete the 3 dead
variants outright** (see Op. 6) since default never reaches them.
**Risk:** MEDIUM for the function-constant route; LOW for deletion.

### ★★★ Opportunity 3 — Consolidate the 4 NVFP4 O-proj kernels (this one IS default-relevant)
**Target:** `lagunaGatedAffineOProjNVFP4Kernel` (4085), `lagunaGatedAffineOProjNVFP4HalvedKernel`
(4098), `lagunaActivatedOProjKernel` (4197), `lagunaActivatedOProjHalvedKernel` (4209).
**Evidence:** Generated by one function `lagunaGatedAffineOProjNVFP4Source(
preActivatedGate: Bool, halvedScales: Bool)` (see 4075-4220). Differ by two booleans:
`halvedScales` (1 byte/32 vs 1/16 scale read + `oproj_escape` input) and `preActivatedGate`
(softplus inside vs pre-activated). Dispatch (4231-4242): `halved=lagunaOProjScaleHalvingEnabled`
(ON), `gateIsActivated` from the QKV path. **Default decode: `lagunaActivatedOProjHalvedKernel`
(4209)** (gateIsActivated=true, halved=true). The non-halved pair (4085/4197) is dead
under halving ON; the non-activated pair is dead when g_proj fuses the gate.
**Savings:** The 4-way matrix collapses to **1 default compile**, but the kernel_name
already encodes the `_hs1`/`_sc1`/`_se1` suffixes (4087-4102, 4199-4213) so each
combination is distinct. If the harness ablates halving (`DARKBLOOM_OPROJ_SCALE_HALVING=0`)
it recompiles a 2nd. Consolidating to 1 via runtime halving-branch would cap it at 1
regardless of flag state. **Real savings: 0-1 default, up to 3 under ablation.**
**Fix:** make `halvedScales` a runtime `if (halved)` branch inside one kernel (the
address-arith diff is small, 4449-4471) OR delete the 3 non-default variants.
**Difficulty:** MEDIUM (runtime branch risks a divergent load path; bit-exactness must be
re-verified). Deletion is LOW/SAFE.
**Risk:** LOW for deletion (default path kept); MEDIUM for live consolidation.

### ★★☆ Opportunity 7 — Collapse the 2 compiled gate-projection graphs (PR #361 territory)

### ★☆☆ Opportunity 10 — Verify `lagunaSlidingQKNormRoPEKernel` (1143) warmup-compile is unavoidable
**Target:** the standalone sliding QK-norm+RoPE kernel.
**Evidence:** It compiles **only in warmup** (warmup decode steps run at pos<512 where

scored-time `fusedRingPrepare` decline would compile in-window — the exact failure mode
we're avoiding). **Recommend:** leave as-is unless the ring-prepare decline is provably
impossible in scoring; prefer Op. 1 (pure waste) over this.
